## 1. 定量的証拠: 「fix が 1 箇所にしか当たらない」の実測

これまで台帳は個別の事故（`2bda22b`/`394356e`/`fd0cc33` 等）を列挙してきたが、事故が**構造的にどれだけ起きやすいか**は測っていなかった。全255コミットの変更ファイル集合から、既知の兄弟ファイル群について「兄弟の一部だけを触ったコミット（partial）」の割合を算出した:

| クラスタ | 兄弟を触ったコミット数 | 全兄弟同時 | 一部のみ | partial率 |
|---|---|---|---|---|
| J1/C2 投票JS 3ファイル | 24 | 1 | 23 | **96%** |
| C3 CNノート (JS+テンプレ2) | 60 | 1 | 59 | **98%** |
| P2 ORDER BY (comment/vod repo) | 24 | 2 | 22 | **92%** |
| N6/R6 users/vods 兄弟JS | 7 | 2 | 5 | 71% |
| C1 レンダラ (app↔batch) | 12 | 5 | 7 | 58% |

注意: partial 率はファイル粒度の近似であり、片方だけの変更にはファイル固有部分（正当な単独変更）も含まれる。**この数字は「事故率」ではなく「兄弟の存在を意識しないまま片方を編集する機会の頻度」**と読むべきで、その機会が編集の9割超を占めるクラスタでは、共有部分の修正が伝播しないのは確率的必然になる。

### 1-1. C1 の精密分析: 同期規律は「守られていたのに」分岐した

C1（body_html レンダラ）は共有シンボル（`parse_raw_comment` 等）に触れたコミットだけを抽出して精査した。結果は戦略文書の想定より興味深い:

- batch コピーの誕生は `ff8d46a`（2026-03-10、事前レンダリングの **perf コミット**）。重複はリファクタの怠慢ではなく**性能改善の副産物**として生まれた。
- エモートID正規化の**脆弱性修正** `1ab1ccb`（2026-02-25）はコピー誕生**前**だったため、コピーに含まれた。誕生後だったら2箇所適用が必要だった——「セキュリティ修正が片方に残らなかったのは時系列の幸運」である。
- 誕生以降、共有シンボルに触れた5コミットは**全て両ファイルを同時変更していた**。つまり暗黙の同期規律は今日まで守られている。
- **にもかかわらず分岐した。** 台帳が実測したコメント行分岐（`# Emote labels should stay plain text...`）を導入したのは `0ca20a1`（2026-03-11「即時安全修正」）で、このコミットは**両ファイルを同時に触りながら**、コメントを app 側にだけ追加した。

> **教訓（本書で最も重要な発見）: 「同時に触る」ことと「同一に保つ」ことは別物である。** co-change 規律（プロセス、Layer 3）は分岐を防げない。分岐を防げるのは内容 diff の同期ガード（Layer 2.5）だけ。戦略文書の Layer 2.5 最優先という判断は、この考古学によって事後的に強く正当化された。

## 2. 機械走査による台帳の検証と、検出手法自体の監査

台帳の走査手法（同名関数 grep）には理論上の盲点がある: **コピー時に改名されたクローン**（Type-2 クローン）は同名 grep に掛からない。LLM は「似せて書く」ため改名・微修正クローンを生みやすいという仮説も立つ。これを検証するため、全 Python 関数（4文以上）の AST を正規化（識別子・文字列リテラルを匿名化、コメント・docstring は AST 段階で消える）してハッシュ化し、完全一致グループを機械抽出した（約8.8万関数、`challenge/.venv` 等の外部パッケージ含む）。

### 2-1. 結果①: 台帳のクラスタは全て機械走査でも裏付けられた

C1 の3関数（AST レベルで完全一致＝分岐はコメントのみ、と独立に確認）、R3 `call_analyze_api` ×4（完全一致）、N5 `load_env` ×3、R3 `fetch_comments` は 2 一致+1 分岐（`pipeline.py` 版が乖離——台帳の ASC/DESC 分岐記録と整合）。

### 2-2. 結果②: 本番コードに「改名クローン」は存在しない——シンボル台帳方式の実証

プロジェクト固有コードで改名クローンは**検出ゼロ**（唯一の例外は UI テストの自明な3関数）。つまり**現時点では同名 grep ベースの CI ガードで全クローンを捕捉できる**。戦略文書が「AST 解析より シンボル台帳の方が確実」とした判断は、勘ではなく実測で支持された。

ただし対照群が警告を与える: 同じ走査で `challenge/.venv` 内の成熟ライブラリ（torch / transformers / sympy）からは**改名クローンが数百件**検出された（例: transformers の `rotate_half` 系 14 実装、`inverse_sigmoid` 10 実装）。コードベースが成熟・大規模化すると改名クローンは必ず発生する型であり、**同名 grep の有効性は「今このリポジトリだから」成立している時限的な性質**である。→ 対策: 本走査スクリプトを `ci/clone_scan.py` としてコミットし、**非ブロッキングの定期棚卸し（月次）を機械化**する。戦略文書 §5 の「網羅性は定期棚卸しで補う」を人手作業から自動化に格上げする。

### 2-3. 結果③: 新クラスタ2件——台帳の「シロ判定」の訂正

**T1. 🟡 テスト基盤 conftest の4関数クローン**
台帳 R1-R7 の走査は「テストは `tests/integration/helpers.py` に seed 関数が集約済み」としてテスト層をシロ判定したが、これは seed 関数しか見ていなかった。実際には [`app/tests/ui/conftest.py`](../app/tests/ui/conftest.py) と [`app/tests/integration/conftest.py`](../app/tests/integration/conftest.py) に `_clear_all_tables` / `apply_migrations` / `db_engine` / `db` の**4フィクスチャが AST 完全一致で二重定義**され、`_load_check_schema_module` も unit/integration の test_schema_check.py に二重。分岐リスクは具体的: マイグレーション適用や TRUNCATE 手順が suite 間でズレると「integration は通るが ui は落ちる（またはその逆）」というテスト基盤起因の偽陽性/偽陰性になる。テストは「重複を検出する側」の装置なので、**検出装置自体の分岐は他のクラスタより性質が悪い**。

**M1. ⚪ 指示層のメタ重複: AGENTS.md ↔ CLAUDE.md**
`AGENTS.md`（4行）は `CLAUDE.md` の `# Test` 節の**逐語コピー**（末尾改行のみ差）。つまり「LLM への指示」という層自体がすでに重複しており、テスト実行ルールを変えると2ファイル更新になる。これは小さな実害だが、**戦略文書 Layer 3 の前提「CLAUDE.md は LLM が毎セッション読む唯一の場所」を偽にする**点で重要（§4-3 で詳述）。

## 3. C1 の訂正: emote 仕様は4実装ではなく5実装、そして「実装間の暗黙契約」という新しい欠陥クラス

台帳は emote 描画仕様を「Python 2 + JS 2 の計4実装」と数えたが、走査で5つ目が確認された: [`comment_utils.py:18`](../app/services/comment_utils.py#L18) の `_BodyHtmlSanitizer`（`_ALLOWED_SRC_PREFIX` / `_ALLOWED_IMG_ATTRS` を独自保持）。これは batch 側には存在しない app 専用のサニタイザで、JS の `appendSafeBodyHtml` と**同一の許可リストを Python で再実装**したものである（リテラル箇所は CSP・sw.js・テスト込みで計8箇所）。

数の訂正より重要なのは、ここに**台帳の分類に無い欠陥クラス**が見えること。[`decorate_comment`](../app/services/comment_utils.py#L267) は保存済み `body_html` も実時レンダ結果も `sanitize_body_html` に通す。つまり:

> **レンダラ（2実装）の出力は、サニタイザ（Python 1 + JS 2 実装）の許可リストを通過できなければならない**——という契約が、どこにも明文化されないまま5実装に分散している。

レンダラに属性を1つ足す（例: `width`/`height` で CLS 対策）と、バグも例外も出ずに、**3つのサニタイザが黙ってそれを剥ぎ取る**。「片方だけ直って片方にバグが残る」（分岐）とは別種の、「全部が仕様通り動いた結果として壊れる」（契約破り）事故である。台帳の🔴/🟡分類は分岐リスクを測るが、この**協調不全リスク**は捕捉しない。→ C1 統合時は、レンダラとサニタイザを同一モジュールに置き、「レンダラ出力はサニタイザを恒等通過する」ことを property test（renderer(x) == sanitize(renderer(x))）で固定するべき。

## 4. 外部研究との接続: この問題は個別事例ではない

### 4-1. 業界データ: AI 支援開発は重複を計測可能なレベルで増やしている

[GitClear の 2025 年調査](https://www.gitclear.com/ai_assistant_code_quality_2025_research)（2020〜2024 の 2.11 億変更行）は、AI コーディング支援の普及と並行して: 重複コードブロックの頻度が **8 倍**に増加、copy/paste 行の比率が 8.3%→12.3%、**リファクタリング（moved 行）は 24.1%→9.5% に激減**し、2024 年に copy/paste が moved を史上初めて逆転したと報告している。本リポジトリの36+2クラスタは開発スタイルの個別的失敗ではなく、**LLM 駆動開発の既知のシステム的傾向**の一標本であり、だからこそ「注意する」でなく「機構で防ぐ」（戦略文書 Layer 2）が正しい。AI 生成 PR がコード再利用を減らす傾向は査読研究でも観測されつつある（[More Code, Less Reuse, arXiv:2601.21276](https://arxiv.org/html/2601.21276)）。

### 4-2. 古典研究: 「危険なのは分岐」テーゼには20年の実証がある

戦略文書 §1-4 の教訓「危険なのは重複ではなく分岐である」は、クローン研究の古典 [Juergens et al. "Do Code Clones Matter?" (ICSE 2009)](https://dl.acm.org/doi/10.1109/ICSE.2009.5070547) の主結果そのものである: 商用システムの調査で**クローンの約52%が不整合に変更**され、**非意図的な不整合変更のおよそ半分が欠陥**だった。本リポジトリで実測された「最低3回の fix 取りこぼし」は、この確率過程が小規模リポジトリでも十分に回ることを示す。

もう一つ重要なのが Kapser & Godfrey の "'Cloning Considered Harmful' Considered Harmful"（Empirical Software Engineering, 2008）で、**合理的なクローン**のパターン分類（forking / templating / customization）を与えた。challenge/ の「1ファイル完結配布」は典型的な **forking パターン**であり、戦略文書 Layer 4（意図的コピーの登録簿）は経験則ではなくこの分類学の実装として位置づけられる。区別の基準も文献から借りられる: **独立に進化することが期待されるか**（forking＝許容）、**同一であり続けることが期待されるか**（事故コピー＝禁止 or 同期ガード）。

## 5. 戦略文書のレッドチーム: 前提の実地検証で見つかった4つの穴

### 5-1. §3-2 案(a)「compose 2行 + COPY パス修正のみ」は過小評価——`additional_contexts` を推奨に差し替え

実測: `build: ./app` は **dev 4 サービス + prod 1 サービスの計5定義**（docker-compose.dev.yml / docker-compose.yml）。さらに重大なのは、ルートをビルドコンテキストにすると `challenge/.venv`（**実測 7.6GB**、torch 入り）が候補に入ること。ルートの `.dockerignore` は `.venv` を持つが、dockerignore のパターンはルート相対なので **`challenge/.venv` にはマッチしない**（`**/.venv` が必要）。batch は既にルートコンテキストであり、BuildKit の遅延転送で顕在化していないだけで、現状でも地雷である。

**修正提案**: Docker Compose は本環境で 5.1.4 であり `build.additional_contexts` が使える。app の `build: ./app` を維持したまま

```yaml
build:
  context: ./app
  additional_contexts:
    shared: ../shared
```

`COPY --from=shared . /app/shared/` とすれば、**5サービスのコンテキスト変更なし・7.6GB 問題に触れずに** shared パッケージを両デプロイへ供給できる。案(a) より侵襲が小さく、案(b) の「依存の向きの不自然さ」も無い。併せて `.dockerignore` に `**/.venv` / `node_modules` / `challenge/` を追加する（これは shared 化と無関係に今すぐやるべき修正）。

### 5-2. 単一定義はコード分岐を消すが「デプロイ分岐」は消さない

shared パッケージ化しても app と batch は**別々にビルド・デプロイされる**事実は変わらない。レンダラ変更後、片方だけ再デプロイされた期間は、実行中バイナリのレベルで C1 と同じ二重実装状態が復活する（保存 body_html の version 不一致は app 側の再レンダで graceful に吸収されるが、事前レンダの perf 効果はその間失われる）。つまり §3-2 の運用ルール（version インクリメント + backfill 実行）は **shared 化後も恒久的に必要**であり、「集約したから終わり」ではない。Done 定義に「(f) デプロイ手順（両サービス再ビルド + backfill）が README/CLAUDE.md に記録されている」を足すべき。

### 5-3. §3-4 `<template>` 方式は markup の重複は消すが「データバインディングの重複」が残る

`<template>` + cloneNode 方式でも、**どの値をどのスロットに流し込むか**は Jinja（マクロ引数の `{{ }}` 展開）と JS（cloneNode 後の querySelector への代入）の2箇所に残る。スロットの追加・改名で「サーバ初期描画には出るが JS 追加読込分に出ない」という C3 型の分岐が**バインディング層で再発**しうる。緩和策: スロットのアドレッシングを `data-field="vote-count"` のような**単一の属性体系**に統一し（Jinja も JS も同じ `data-field` を埋める/引く）、案(iii) の golden test（サーバ描画 vs JS 描画の DOM 一致）を**代替ではなく補完として常設**する。テンプレ方式を採っても (iii) は捨てないこと。

### 5-4. Layer 3 の前提「CLAUDE.md が唯一の場所」は偽（M1）——さらに、規範はフックで機械化できる

M1 の通り AGENTS.md が既に並存しており、ツールによってどちらを読むかが違う（Claude Code は CLAUDE.md、他エージェントは AGENTS.md を読む慣行）。**修正フローの正本を2ファイルに書けば、修正フロー文書自体が分岐する**——この皮肉を避けるため、ルールの正本は CLAUDE.md に置き、AGENTS.md は「CLAUDE.md を参照」の1行にする（または同期ガード対象にする）。

さらに一歩進められる。このリポジトリには既に PostToolUse lint フック（`.claude/hooks/post_tool_lint.sh`）が動いている前例がある。同じ機構で、**編集されたファイルを `ci/duplication-baseline.txt` のクラスタ表と突き合わせ、「このファイルには兄弟がいる: …」を編集直後に自動注入するフック**を追加できる。これにより Layer 3 の中核（兄弟実装の想起）が、LLM の注意力・コンテキスト残量・CLAUDE.md を読んだかどうかに**依存しなくなる**。baseline ファイルは「CI ガードの入力」と「LLM 向け兄弟インデックス」の二役を担う単一の真実になり、戦略文書の設計思想「人（LLM）の注意力を最後の砦にしない」が Layer 3 自体にも適用される。

### 5-5. （追認）越境 golden test はパッケージ化を待たずに今日書ける

[`app/tests/unit/test_generate_community_notes.py`](../app/tests/unit/test_generate_community_notes.py) が `importlib.util.spec_from_file_location` で **batch スクリプトを直接ロードしてテストする前例**を既に持っている。Phase 1 の golden test（app/batch 双方のレンダラに同一入力→出力一致）はこのパターンで**即日**書ける。手順を「① golden test（既存パターン流用）→ ② 同期ガード → ③ shared 化（additional_contexts 方式）→ ④ ガード切替」と精密化し、①と②の順序を戦略文書から入れ替える（テストが先にあれば同期ガードの導入自体が安全になる）。

## 6. メタ考察: 台帳・戦略・本書という「文書群」自体が重複し始めている

台帳は自ら認める通り行番号が既にドリフトしており、本書の追加でクラスタの事実が3文書に散在し始めた。**コードの重複と同じ力学が文書にも働く**（M1 はその最小例）。原則を1つ定める:

> 機械検証可能な事実（クラスタのシンボル名・ファイル集合・許容例外）の正本は `ci/duplication-baseline.txt` とし、文書はクラスタ ID と考察だけを持つ。台帳の「現存確認」は人手の再走査ではなく `ci/clone_scan.py` の定期実行結果で行う。

これにより「台帳・ベースライン・コードの3点一致」（戦略文書 §4）は、維持コストの掛かる規律から、**ベースラインを起点にした自動導出**に近づく。

## 7. 結論: ロードマップへの反映

優先順位の大枠（C1 → J1 → J2 → …）は全検証を通じて揺らがなかった。変更点のみ:

1. **Phase 0 に追加**: `.dockerignore` の `**/.venv` 等追記（即日・独立）／M1 解消（AGENTS.md を参照化）／兄弟リマインダーフック（baseline 完成後）／`ci/clone_scan.py` のコミットと月次棚卸しの機械化。
2. **Phase 1 の手順精密化**: golden test を同期ガードより先に（§5-5）。shared 供給は案(a) から **additional_contexts 方式（案a'）**に差し替え（§5-1）。C1 統合時に renderer↔sanitizer の恒等 property test を追加（§3）。Done 定義に (f) デプロイ手順の記録を追加（§5-2）。
3. **Phase 5（CN表示系）**: template 方式に golden test を併設し、`data-field` アドレッシングを採用（§5-3）。
4. **台帳に T1（テスト conftest）を🟡で、M1（指示層）を⚪で追加**。テスト層のシロ判定を撤回。T1 は Phase 4 前後で回収（テストを触る Phase の直前が効率的）。
