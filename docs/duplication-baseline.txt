# duplication-baseline.txt — 重複クラスタのベースライン台帳（機械検証可能な事実の正本）
#
# 位置づけ: duplication-remediation-strategy.md §2 Layer 2（ラチェット方式）の入力。
#   duplication-verification-and-critique.md §6 の原則に従い、クラスタのシンボル名・
#   ファイル集合・許容例外の正本は本ファイルとし、3文書はクラスタ ID と考察のみを持つ。
#   戦略文書は最終配置を ci/duplication-baseline.txt と定めている。ci/check-duplication.sh
#   実装（Phase 0）の際に ci/ へ移動し、docs/ からは参照リンクに置き換えること。
#
# 形式: タブ区切り4列
#   <cluster>	<kind>	<pattern>	<allowed-files（カンマ区切り、リポジトリルート相対）>
#   kind: fn-py / fn-js = 関数定義（def <sym>( / function <sym>( 相当。window.<sym> = も含む）
#         const = 定数定義 / literal = 固定文字列 / sql = SQL断片 / css = セレクタ定義
#         markup = HTML断片 / files = パターン検査なし（兄弟リマインダーフック用の紐付けのみ）
#   pattern が「-」の行は grep 検査対象外（kind=files）。それ以外は fixed-string 検索を想定。
#
# 運用（ラチェット）:
#   1. allowed-files に無いファイルに pattern が現れたら CI fail（新規増殖の禁止）
#   2. クラスタを共通化した PR で該当行を削除する。削除した行は二度と追加しない
#   3. 行数の合計がそのまま重複の残債メトリクスになる
#   4. ファイル集合の変更（正当な理由がある場合のみ）は PR で理由を明記する
#
# 本ファイルのファイル集合は 2026-07-04 の grep 実測値。台帳の記載と異なる箇所（実測の方が
# 広い）: R1 の MYSQL_HOST は batch 5 + morpheme-sample 3、R4 はテスト含め 4、R5 の
# .page-header は manual.css 含め 5（manual は同名別ルール）、C2 の投票markupは JS 2 + テンプレ 3、
# J3 の root_path 供給要素は root-path-data（JS 8 + テンプレ 8 + テスト 1）と app-root-path
# （base.js + base.html）の2系統が並存（台帳未記載の分岐。quiz.html は cfg JSON、
# offline-access.js は独自ヘルパでさらに別系統）。
# 台帳未記載でベースライン検証時に新たに検出した増殖:
#   - R6: .filter-bar の同一ルールが index.css(805) にもある（計3コピー、台帳は2）
#   - C5: 5軸ラベルの真のマスタは batch/prompts/community_note_system_prompt.txt（LLM への
#     出力指示）。C5 も C4 と同型の app↔batch 境界越えクラスタである（台帳は app 側4箇所のみ記載）
